#### Design Specificity Verdict

**LLM assessment:** This could be swapped onto almost any developer's name with zero other changes and nobody would notice. The visual language — one indigo accent, `rounded-2xl` bordered cards, Geist Sans, an eyebrow/headline/two-pill-CTA hero — is the default aesthetic of any Next.js+Tailwind portfolio scaffold from the last two years. Nothing in the five components visually reflects what was actually built: a photography booking site, a piñata/candy e-commerce configurator, a Flutter wellness app, a native Android habit tracker, and a Flask/Arduino robotics rig all get the identical grey-bordered card. The irony: `data/projects.ts` itself *describes* VitaMind's real design ("Deep Teal and Coral... Fraunces and Inter... glassmorphic UI") — a distinctive identity that exists in the case-study copy but is completely absent from the portfolio's own design. Geist Mono is loaded as a CSS variable and never used — a missed chance to give the hardware/robotics entry a distinct technical voice. This is the single biggest risk to the site's own stated purpose of demonstrating "breadth" to two audiences who are, per PRODUCT.md, scanning quickly.

**Deterministic scan:** `node detect.mjs --json app components` — exit code 0, findings: `[]` (clean). The mechanical antipattern detector found nothing at the code/markup level. This is expected and not reassuring on its own: a generic-but-tidy implementation doesn't trip rule-based checks the way visible slop (contrast failures, banned patterns) would. Clean detector + a strong specificity finding from the LLM assessment are not in conflict — they're evidence of different failure modes, and this project has the second one, not the first.

**Visual overlays:** Injection did not succeed. The browser tool's tab reached a preflight-confirmed working state (mutation test passed: title + script injection both verified), but immediately after the detector's live-server started, every subsequent navigation to `localhost:3000`/`127.0.0.1:3000` in that Chrome instance resolved to `chrome-error://chromewebdata/` across 5 retries and 2 tab groups — while the dev server itself stayed healthy throughout (confirmed 200 via `curl`/`Invoke-WebRequest`, and the same tab loaded `example.com` fine). This reads as an environment-specific navigation fault tied to the live-server starting, not a missing tool or a mutation-capability problem. No reliable user-visible overlay is available from this run; no console-based overlay findings exist to report.

#### Overall Impression

The build is clean, accessible-by-default in the boring ways (semantic dialog, no error states to get wrong), and well-organized — but it's generic where it most needs to be specific. The gut reaction: this is a competent scaffold, not yet a portfolio. The single biggest opportunity is giving each of the 5 projects a visual identity that matches its actual case-study content, instead of routing all five through one identical card/dialog treatment.

#### What's Working

- **`ProjectDetail.tsx`'s native `<dialog>` implementation** — `showModal()`, backdrop-click-to-close, and free Esc handling is a well-chosen, low-risk pattern over a hand-rolled modal.
- **Content honesty in `data/projects.ts`** — BroadIntern's outcome ("an experimental voice-command layer was added but never fully verified. Shelved after the initial build sprint") is refreshingly non-inflated, matching PRODUCT.md's "no fabricated metrics" principle.
- **The hover-reveal CTA concept on `ProjectCard.tsx`** is a reasonable low-cost affordance idea on desktop — the instinct (signal the card is clickable) is right; the execution is a P1 issue below.

#### Priority Issues

**[P0] Interchangeable visual identity**
- **Why it matters:** PRODUCT.md's own positioning is "differentiated by breadth" — but that claim only exists in the text, not the design. A visitor scanning fast (exactly how both target audiences are described) gets a visual signal of sameness that undercuts the pitch.
- **Fix:** Add at least one visual artifact per project (real screenshot, a device frame for the two mobile apps, a sensor-chart sketch for BroadIntern); put the already-loaded, unused Geist Mono to work as a deliberate technical accent on the hardware/robotics entry instead of leaving it dead.
- **Suggested command:** `$impeccable adapt`

**[P1] Hidden mobile affordance — "View case study" is invisible on touch**
- **Why it matters:** `ProjectCard.tsx`'s only textual CTA uses `opacity-0 ... group-hover:opacity-100`, which never fires on touch devices. Mobile visitors get a tappable card with zero pre-tap signal of what tapping does.
- **Fix:** Make the CTA text always visible at small viewports (`opacity-100 sm:opacity-0 sm:group-hover:opacity-100`), or swap the opacity reveal for a persistent low-emphasis affordance with a hover-only color shift.
- **Suggested command:** `$impeccable polish`

**[P1] Wall-of-text case-study dialog**
- **Why it matters:** The dialog is the moment of highest visitor interest — exactly where both audiences most need a fast, confident read — yet Problem/What I Built/Outcome render as three undifferentiated dense paragraphs (FM Media's alone strings 9+ technical nouns into one block).
- **Fix:** Visually promote the Outcome line, break "what I built" into 3-4 short bullets instead of a paragraph, give the three sections distinct visual weight instead of identical `dt`/`dd` styling.
- **Suggested command:** `$impeccable clarify`

**[P2] Ragged card grid from unbounded content**
- **Why it matters:** `oneLiner` has no `line-clamp` and the card has no shared min-height, so a longer one-liner or extra stack tag misaligns card bottoms across the 2-column grid — and this only gets worse as more projects are added.
- **Fix:** `line-clamp-2` on the one-liner, pin the CTA to the bottom with a flex spacer, give cards a shared min-height.
- **Suggested command:** `$impeccable polish`

**[P2] Inconsistent, incomplete focus/AT wiring**
- **Why it matters:** `ProjectCard.tsx` defines a custom focus-visible ring, but the nav links, Hero CTAs, Contact's mailto link, and the dialog's close button all fall back to browser default — and the `<dialog>` has no `aria-labelledby` tying it to the project title, so a screen-reader user isn't guaranteed an announced name for the modal.
- **Fix:** Standardize one focus-visible treatment across all interactive elements; add `aria-labelledby` on the `<dialog>` referencing the title `h3`.
- **Suggested command:** `$impeccable harden`

#### Persona Red Flags

**Casey (mobile):** The "View case study →" affordance never renders before tap on any touch device. Also, the dialog's × close button sits inside the same scrollable container as the case-study content (`max-h-[80vh] overflow-y-auto`) rather than pinned — once a mobile user scrolls down to read, the only remaining exit is tapping the backdrop (undiscoverable) or scrolling back up.

**Sam (accessibility-dependent):** Focus-visible styling exists only on the project card button; every other interactive element falls back to default, an inconsistent keyboard experience on one small page. The dialog has no `aria-labelledby`, leaving its accessible name to browser/AT guesswork.

**Jordan (first-timer, cold landing):** With zero screenshots anywhere on the site, Jordan has to open all 5 dialogs and read dense paragraphs just to understand what was built — the opposite of PRODUCT.md's own description of this audience as "quickly scanning." The two anonymized client projects have no screenshot, live link, or client name by design (a legitimate confidentiality call), but nothing else rebuilds that trust signal, so ~40% of the showcased work is taken purely on faith.

#### Minor Observations

- `Contact.tsx`'s `© {new Date().getFullYear()}` is computed at build/render time with no revalidation wired — if the site is built once and not rebuilt, the year goes stale.
- Light-mode accent-on-background contrast (`#5b5bf0` on `#fafafa`) computes to roughly 4.8:1 — technically passes WCAG AA for normal text but is close, and it's used on small text (hero eyebrow, status pill, card CTA).
- The arrow/× glyphs are raw HTML entities rather than SVG icons — functionally fine, but ties their rendering weight to the visitor's system font.
- Hero and Contact both carry their own CTA with slightly different copy ("Get in touch" vs. "Want to work together?") — reasonable reinforcement, just worth being intentional about.
